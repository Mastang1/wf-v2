# 3　按实际岗位倒推：你应该从源码拿走什么

目标不是背下 wolfBoot 所有宏，而是能解释并验证：“收到一个新固件后，谁决定它可信、写到哪里、何时替换、掉电之后怎么继续、运行失败怎样恢复？”你已有的寄存器、UART、Flash 和中断经验是入口；新增的是跨复位持久化状态、镜像信任和发布系统的接口。

驱动写得好并不自动等于更新可靠：驱动通常在本次运行内完成事务，Bootloader 的事务可能跨很多次复位。需要把“上一条写命令是否已经落盘”变成可恢复的状态，而不是靠 RAM 变量记忆。

## 先带着这些问题看源码

1. **信任入口**：reset 后第一段可变代码在哪里？F407 没有 Cortex-M33 TrustZone；如果攻击者能改 Bootloader 和公钥，验签还剩什么意义？
2. **存储契约**：分区起点与物理 Sector 是否一致？trailer 被谁擦？应用大小上限是否在下载前和认证前都检查？
3. **独立构建契约**：APP 向量表是 0x08020100 还是分区起点？APP/Bootloader 的算法、地址、头大小是否来自同一发布配置？
4. **认证契约**：Header/Hash/签名分别能说明什么？镜像里的公钥 hint 是否可自行成为信任根？代码在哪里限制密钥授权分区？
5. **更新契约**：下载完成是否就切换？为什么 trigger 必须在文件写完后？下载传输成功与内容可信如何分开？
6. **恢复契约**：交换中哪份副本最后才允许擦？状态写在数据前还是数据后？什么时候重复操作是安全的？
7. **运行契约**：谁判断新版健康？不确认后要到哪一次 reset 才回滚？watchdog 没有触发时 Bootloader 能做什么？
8. **版本契约**：正常更新拒绝同版/旧版与测试失败回滚旧版怎样共存？Flash 中版本号是否等价于硬件单调计数器？
9. **板级契约**：换板仅改 LED 是否足够？时钟、VDD/Flash latency、写粒度、复位、Flash stall、中断和 DMA 谁负责？
10. **发布契约**：私钥丢了/泄露了怎么办？工厂、公钥轮换、售后恢复和调试权限如何匹配？

第 4～6 篇分别给出静态结构、时序和文件位置。每次阅读以“输入、校验、产生的持久化状态、失败后剩下什么”为四个问题，不需要从每个 `#ifdef` 一路线性读到底。

## 产品里到底是不是只改 BSP

同型号、相近板级电路、相同存储方案时，官方 HAL 能显著减少寄存器工作；本包即复用其内部 Flash 驱动。但“只改 BSP 就行”仍不完整：本次已看到示例时钟、APB 分频、串口 AF 和最新状态扇区策略需要复核。产品还需要下载协议、APP 链接/中断策略、健康确认、watchdog、密钥保护、量产烧录和故障验收。

你可以沿用官方 Makefile 构建 Bootloader，用自己现有工程独立构建 APP；两套构建没有必须合并的理由。共用的是镜像契约与发布流水线，不是所有业务代码。保留 upstream 的构建有利于升级和复证，板级修改用小 patch/独立 target 管理。换外部 QSPI、双 Bank 或 RTOS 后，要重新检视契约，而不是只把 `TARGET` 字符串改一下。

UDS/CAN 是某类岗位的协议要求，不是 wolfBoot 核心本来就提供全部汽车诊断栈。普通 STM32F4 test-app 的 UART demo 只用于学习；它不自动满足 UDS、安全诊断会话或产品 OTA 后端需求。
